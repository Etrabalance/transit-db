## 1. Фильтрация и сортировка

Запрос №1 нашёл **25 маршрутов длиннее 20 км**. Самый длинный из выведенных — учебный `W4-40`, **36,00 км**. Запрос №4 нашёл **4 автобусные модели** вместимостью от 40 до 90 пассажиров.

**`LIKE` и `ILIKE`.** Запросы №2–3 ищут остановки с началом «Аль» и показывают по **15 строк**. В данной версии №2 применяет `LIKE 'Аль%'`, а №3 — `ILIKE 'аль%'`. Одинаковый результат связан с тем, что в данных совпадают варианты, начинающиеся с заглавной «А». Разница операторов: `LIKE` учитывает регистр, `ILIKE` — нет. Например, с *одним и тем же* шаблоном `аль%` значение `Аль-Фараби` совпадёт при `ILIKE`, но не совпадёт при `LIKE`. Для явной демонстрации можно выполнить:

```sql
SELECT 'Аль-Фараби' LIKE 'аль%' AS matches_like,
       'Аль-Фараби' ILIKE 'аль%' AS matches_ilike;
-- Ожидается: false, true
```

## 2. Особенности NULL на реальных данных проекта

Из **500** водителей у **50** не заполнен телефон (`phone IS NULL`). Запросы вернули:

| Условие | Результат |
|---|---:|
| `phone IS NULL` | **50** |
| `phone <> '+77010000001'` | **449** |
| `phone IS DISTINCT FROM '+77010000001'` | **499** |

**Почему `<>` не находит NULL?** Сравнение с `NULL` возвращает не `TRUE` и не `FALSE`, а `UNKNOWN`. Условие `WHERE` оставляет только строки с `TRUE`, поэтому неизвестные телефоны исключаются. Исправление зависит от цели: `IS NULL` показывает неизвестные номера, а `IS DISTINCT FROM` включает NULL среди значений, отличных от заданного номера.

`COALESCE(phone::text, 'Телефон не указан')` превращает отсутствие телефона в понятную подпись. `NULLIF(btrim(COALESCE(middle_name,'')), '')` превращает пустое отчество в `NULL` после очистки пробелов.

## 4. Работа с датой и временем — 11 примеров

Запросы №12–20 и №25–26 охватывают требуемые операции:

1. **№12:** рейсы за вчера через `CURRENT_DATE` и граничные значения времени.
2. **№13:** количество рейсов текущего месяца через `date_trunc('month', CURRENT_TIMESTAMP)`.
3. **№14:** рейсы за последние семь дней через `INTERVAL '7 days'`.
4. **№15:** фактическая длительность рейса: `EXTRACT(EPOCH FROM (actual_end_at - actual_start_at))/60`; в выборке — **6,00 минут**.
5. **№16:** группировка GPS по часам через `date_trunc('hour', observed_at AT TIME ZONE 'Asia/Almaty')`.
6. **№17:** рейсы по дням недели через `EXTRACT(dow FROM ...)`; в первой неделе 2025 года выведено по **480 рейсов** на каждый из семи дней.
7. **№18:** рейсы в субботу и воскресенье за 2025 год — **49 920**.
8. **№19:** один момент в UTC и Алматы с `AT TIME ZONE`. Например, `2025-01-01 01:00 UTC` соответствует `2025-01-01 06:00` в Алматы.
9. **№20:** календарь всех **31** дней октября 2026 года через `generate_series`, включая дни без рейсов.
10. **№25:** группировка рейсов по месяцам 2025 года; январь — **14 880**, февраль — **13 440**.
11. **№26:** задержка старта рейса, рассчитанная как разность двух `timestamptz`; для показанных записей — **1,00 минута**.

**Почему запросы за вчера / текущий месяц / последние 7 дней дали 0?** Большой учебный набор содержит рейсы **2025 года**, а команды запускались **12.10.2026**. Отсутствие строк в заданном диапазоне не является ошибкой.

### Что хранит `timestamptz`?

Тип `timestamptz` хранит **конкретный момент времени**, нормализованный для корректного сравнения, но **не сохраняет название исходного часового пояса**. Отображение зависит от временной зоны сессии, либо от явно указанной зоны через `AT TIME ZONE`. При вычислении интервала вычитаются реальные моменты времени. Для эффективной фильтрации предпочтительно сравнивать индексируемый столбец с границами периода, а не оборачивать его в `date(...)` в условии `WHERE`.

## 5. LIMIT/OFFSET и keyset-пагинация

Запрос №21 показывает вторую страницу справочника остановок: `ORDER BY id LIMIT 20 OFFSET 20`. При `OFFSET 100000` серверу приходится пройти и пропустить много подходящих строк; поэтому глубокие страницы могут быть медленными. В запросе №22 применена **keyset-пагинация**: `WHERE id > 800020 ORDER BY id LIMIT 20`. При индексе по `id` PostgreSQL обычно может продолжить просмотр сразу после последнего показанного ключа. В обоих случаях важен стабильный `ORDER BY`.
